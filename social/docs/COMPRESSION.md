# Compression before live upload

The real Create form prepares sharing copies locally, before any upload. The source file stays on the user's device during preparation. The prepared file goes through the existing authenticated upload, moderation, privacy and quota checks.

- Photos: automatic resize/re-encode to WebP with transparency and orientation support. It targets a compact sharing copy, tries progressively smaller dimensions/quality, and never selects an output larger than the original. Bounded header parsing rejects malformed files, animated WebP and photos over 32 megapixels before browser decode. Supported source types are JPG, PNG and WebP. Existing compact originals can remain unchanged.
- Video: the user explicitly presses **Compress video**, allowing the browser's audio encoder to start after a user gesture. Canvas and MediaRecorder make a lower-resolution sharing copy with audio, a duration-aware bitrate budget and repaired WebM duration metadata. Supported input types are MP4 and WebM. Encoding takes approximately playback time and pauses when the tab is hidden. Cancellation stops playback, encoder tracks, audio nodes and object URLs. Browser codec support and device resources vary; unsupported browsers fail with a clear message.
- Sources may be up to 1 GiB. This is an input-file ceiling, not a guarantee that every 1 GiB source is decodable or compressible to the live storage limit. Very large images, malformed media and excessively long clips are rejected rather than truncated or silently uploaded at an unusable target bitrate.
- The form shows the real before/after bytes and a preview. **Use original** is available when it fits. **Save smaller copy** lets the user keep the exact prepared file for later multipart resume.

While external storage remains unconnected, each prepared upload must fit 8 MiB, and the existing D1 aggregate/member quotas still apply. Compression saves actual bytes but cannot promise a fixed reduction ratio or free unlimited storage. A 1 GiB high-bitrate short clip may shrink substantially; a long or already efficient video may not fit. The form asks for a shorter clip when the bitrate budget is insufficient.

The legacy D1 adapter already stores media chunks as Base64 text. Base64 encodes every three bytes as four characters, increasing data size by about one third; it is not compression. Encoding a file as text does not bypass provider capacity limits. See https://datatracker.ietf.org/doc/html/rfc4648#section-4 .

Implementation: `src/media-prepare.js`, browser-native canvas/Web Audio/MediaRecorder, and the MIT-licensed `@fix-webm-duration/fix` utility bundled locally. No compression service, remote upload, CDN script, new account, or paid provider is used during preparation. Existing still-image optimization is lossy and can change dimensions; the user reviews the resulting copy before posting. Browser-generated video is also lossy. These are not archival backups of originals.

Checks include bounded header/bitrate/cancellation unit tests and real Chrome encoding. Synthetic fixtures demonstrated a 15,482,392-byte PNG becoming 874,662 bytes and a six-second oversized WebM becoming a smaller playable file with audible audio and a finite duration. These controlled fixtures do not predict savings on every real photo or video. End-to-end checks cover original-size rejection before preparation, video cancel/retry, both media types reaching private moderation, owner access, guest denial and temporary-account/media deletion.
